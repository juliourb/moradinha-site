## Desvios da SPEC e por quê

- **Contraste do `--warn` claro ajustado** (`#a8641a` → `#8a5214`): o protótipo aprovado usa `#a8641a` sobre `--warn-soft`, mas essa combinação dá contraste 3,92 (abaixo do mínimo de 4,5 do WCAG AA), pego pelo axe-core na F0-6. Mantida a mesma cor no tema escuro (já passava). Avisar Julio: se quiser manter a cor exata do protótipo, a alternativa é não usar texto nessa cor sobre o fundo suave (só borda/ícone).
- **`<code>` forçado com `!important`** para herdar as cores do design system: o tema `cosmo` do Bootstrap (usado como base) define cor/fundo de `code` que não reagiam ao tema escuro e falhavam o axe-core.
- **Python só para o gerador fictício, em venv isolado** (`.venv-ficticio/`, não versionado): este ambiente não tinha Python de sistema; usado o Python do Anaconda do usuário só para criar esse venv (não alterado o ambiente `moradinha` existente). `h3==4.2.2` pinado exatamente como pede a SPEC_00 §3; `pyarrow`/`duckdb` sem pino na SPEC — registradas as versões exatas obtidas (`pyarrow==26.0.1`, `duckdb==2.0.1`) no `README.md`.
- **`assets/js/duckdb/` (binários do DuckDB-WASM) não é versionado**: são ~75 MB de `.wasm`/`.worker.js` copiados de `node_modules` a cada build (`ferramentas/esbuild.mjs`); versionar infla o repositório sem necessidade, já que o build os recria sempre. Adicionado ao `.gitignore`.
- **`maplibre-gl` e `@duckdb/duckdb-wasm`**: a SPEC pede "fixar na F0 a última estável com pelo menos 2 semanas". Em 22/11/2026: `maplibre-gl@6.17.0` (14,2 dias) e `@duckdb/duckdb-wasm@1.32.0` (a mais recente sem ser pré-lançamento "dev", ~341 dias — as versões mais novas no npm são todas `-devNNN`, não estáveis).
- **`ferramentas/validar.mjs` usa `@duckdb/node-api`, não o pacote `duckdb`** citado como óbvio candidato: `duckdb` exige compilar binário nativo (node-gyp + Python + toolchain C++), indisponível neste ambiente; `@duckdb/node-api` é o binding oficial mais novo, com binário pré-compilado para o Node atual, mesma funcionalidade SQL/Parquet necessária.
- **CRLF×LF quebrava o V2 no CI (1ª rodada do Actions):** `ferramentas/gerar_ficticio.py` grava os JSON com `Path.write_text` em modo texto do Python no Windows, que escreve CRLF; o sha256 gravado em `manifesto.arquivos` foi calculado sobre esses bytes CRLF. O git, sem `.gitattributes`, deixa o autocrlf da máquina decidir a normalização no checkout — no runner Linux do Actions o arquivo chegava com LF, o sha256 batido na hora não conferia com o gravado no manifesto (V2 falhou em 7 arquivos JSON; os `.parquet` e os `.geojson` de uma linha só escaparam porque não tinham quebra de linha para normalizar). Criado `.gitattributes` (`* text=auto eol=lf`; `pacotes/** binary`, para congelar os bytes do pacote exatamente como gerados, em qualquer SO), `git add --renormalize .`, pacotes regerados e revalidados.
- **Ações do GitHub pinadas em versões exatas que já rodam em Node 24** (a run anterior usava `@v4`/`@v3`, que o GitHub está depreciando por rodarem em Node 20): `actions/checkout@v7.0.1`, `actions/setup-node@v7.1.0`, `actions/upload-artifact@v7.0.2`, `actions/upload-pages-artifact@v5.0.0` (composite, sem runtime Node), `actions/deploy-pages@v5.0.1`, `quarto-dev/quarto-actions/setup@v2.2.0` (composite). Versões registradas no `README.md`.
