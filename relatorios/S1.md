- Teste (`tests/unidade/catalogo_montagem.test.js`, 7 casos): o catálogo gerado com os pacotes atuais tem os mesmos
  domínios, edições e padrão do `catalogo.json` de antes (fixture `tests/unidade/fixtures/catalogo_antes_s1.json`).
  **Única diferença:** o `nome` de Maceió passa de "RM de Maceió" (escrito à mão) para "RM de Maceió com a capital"
  (`manifesto.nome` da bd10cbd), como pedido ("nome = manifesto.nome"); o domínio novo é só o teste_sp.
- **Decisão que fica com Julio — `catalogo.json` no git ou não?**
  - *Ficar versionado, gerado e conferido no CI* (como está: o CI roda `npm run catalogo` e `git diff --exit-code catalogo.json`;
    há `npm run catalogo:conferir`). Prós: o diff de um PR mostra que domínio/edição entrou ou mudou de padrão; o
    site funciona em `quarto preview` e nos testes sem passo extra; histórico auditável. Contras: duas fontes
    (manifestos e catálogo) que podem divergir até o CI acusar; quem adiciona um pacote precisa rodar o comando e commitar.
  - *Sair do git (só gerado)*. Prós: fonte única, sem divergência nem commit esquecido. Contras: `quarto preview` e
    os testes passam a exigir o passo de geração antes; mudança de edição padrão não aparece em revisão; `.gitignore` e CI precisam garantir o passo.
  - Pacote por `url` (SPEC_F5 F5-2/3) não é varrido (só pastas de `pacotes/`): se vier, precisa de uma lista à mão em `excecoes.json`.

  domínio eram aplicados; agora só vale o que existe no manifesto do domínio aberto.

- Não há tabela/gráfico por AP com 332 itens: o site usa a AP só por hexágono (CV, ressalva, camada de contornos). A camada de
